# Interview Notes — LAB-011

**Source:** Retrospective Reconstruction

## Purpose

Prepare concise interview talking points from the centralized logging implementation.

## 30-Second Summary

I built centralized logging for the Ubuntu host and Docker environment using Grafana Alloy, Loki, and Grafana. I separated host evidence from container evidence, placed Loki data on dedicated storage, configured an initial 30-day retention period, and kept the logging backend off the host LAN. During validation I discovered that recreating Alloy could replay historical Docker entries, which led me to persist the collector's read-position state rather than judging logging health only by whether the container was running.

## Problem / Business Need

Monitoring could show system state and trends, but it could not answer what happened before or during an event.

The environment needed retained, searchable evidence for operational troubleshooting and future security investigation.

## Technical Approach

The logging pipeline became:

    Ubuntu journal → Alloy → Loki → Grafana
    Docker logs    → Alloy → Loki → Grafana

The design included:

- host journal collection
- SSH/authentication evidence
- Docker container logs
- metadata enrichment
- centralized search
- dedicated Loki storage
- 30-day initial retention
- persistent Alloy collection state
- no direct Loki or Alloy host-LAN publication

## Key Decision

Centralized logs were placed on a dedicated filesystem with bounded retention instead of allowing log growth to consume the root filesystem.

Retention was treated as a capacity decision that should be revised using observed data.

## Troubleshooting / Challenge

After Alloy recreation, historical Docker entries were replayed.

Some were rejected because they fell outside Loki's acceptable ingestion window, and an older entry preceded the configured schema start date.

Persistent Alloy storage and an explicit storage path were added so collection state and read positions could survive container recreation.

## Security / Risk Considerations

Logs can contain security-sensitive operational information and therefore were not exposed unnecessarily to the LAN.

The Docker socket remained a security-sensitive interface even though Alloy mounted it read-only.

The project deliberately stopped at collection and search rather than prematurely adding detection or automated response.

## Interview Questions

### Why did you choose this approach?

Metrics answer questions about system state, while logs preserve event-level evidence. I wanted both capabilities rather than treating monitoring as a substitute for investigation data.

### What would you do differently in a production enterprise environment?

I would define retention from regulatory and business requirements, protect log integrity, establish role-based access, monitor ingestion health and capacity, add redundant storage where required, and build detection and incident-response capabilities on top of validated data.

### What did you learn from the project?

A running collector does not prove healthy logging. Ingestion, timestamps, continuity, metadata, and searchability all need validation.

I also learned that retention policy and storage capacity have to be designed together.

### What was the biggest technical or operational risk?

Assuming logs were being preserved correctly simply because Alloy and Loki containers appeared healthy.
