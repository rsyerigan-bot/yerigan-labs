# Interview Notes — LAB-003

**Source:** Retrospective Reconstruction

## Purpose

Prepare interview talking points from the Ubuntu security-baseline work while distinguishing the original LAB-003 work from later hardening.

## 30-Second Summary

I established an initial security baseline for the Ubuntu Docker host with the goal of reducing attack surface without disrupting required household and management services. The work included firewall and service-exposure considerations, unattended security updates, and documenting current versus future network-security architecture. Later labs improved some exposure controls, but I kept unfinished LAB-003 items explicitly documented rather than retroactively claiming they had been implemented.

## Problem / Business Need

The Ubuntu server was becoming a shared platform for multiple services, so security controls needed to evolve before additional workloads increased the attack surface.

## Technical Approach

The documented LAB-003 work included:

- establishing an Ubuntu security baseline
- documenting current and target network architecture
- defining future security zones
- enabling unattended security updates
- reviewing service exposure
- preserving required management and household functionality
- documenting unfinished follow-on security work

## Key Decision

Security improvements needed to reduce exposure without blindly blocking services the household or administrators actually required.

The project also preserved the distinction between an intended control and a control that was actually implemented.

## Troubleshooting / Challenge

The surviving ENG-003 journal is incomplete.

Later security work reduced some of the same risks through different mechanisms, including tighter service publication and reverse-proxy architecture. The original proposed Docker `DOCKER-USER` filtering was therefore **not** retroactively marked complete.

## Security / Risk Considerations

Firewall status alone does not prove effective service exposure, especially with Docker networking.

Current operational verification therefore considers:

- host listeners
- Docker port publication
- UFW
- IPv4 and IPv6 behavior
- proxy exposure
- network location of the test

## Enterprise Relevance

This demonstrates:

- security baseline development
- attack-surface reduction
- firewall awareness
- Docker exposure analysis
- patching considerations
- documentation of residual risk
- control-validation discipline

## Interview Questions

### Why did you choose this approach?

The server was becoming infrastructure rather than a single-purpose lab system, so I wanted a baseline that balanced security with operational availability.

### What would you do differently in a production enterprise environment?

I would use formally approved hardening standards, configuration management, centralized vulnerability and patch management, external exposure testing, centralized logging, network segmentation, and periodic control validation.

### What did you learn from the project?

A security objective can be partially addressed by later controls without meaning the originally proposed control was implemented. Documentation should distinguish risk reduction from control completion.

### What was the biggest technical or operational risk?

Reducing exposure without accidentally disrupting required administrative, DNS, automation, or household services.
