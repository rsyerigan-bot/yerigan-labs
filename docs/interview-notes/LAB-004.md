# Interview Notes — LAB-004

**Source:** Retrospective Reconstruction

## Purpose

Prepare concise interview talking points from the Caddy reverse-proxy architecture project.

## 30-Second Summary

I replaced direct LAN exposure of several Docker web services with a centralized Caddy reverse proxy. Instead of users connecting to individual IP-and-port combinations, services became reachable through stable friendly names while Caddy communicated with containers over a shared Docker proxy network. This reduced direct host-port exposure and created an abstraction layer for future growth.

## Problem / Business Need

Each service was independently exposed using host ports.

That worked at small scale but created increasing exposure, inconsistent user access, and architectural debt as more services were added.

## Technical Approach

The architecture changed from direct connections such as:

    192.168.1.203:3000
    192.168.1.203:3001
    192.168.1.203:8080
    192.168.1.203:9443

to:

    Browser
      |
      v
    Friendly DNS name
      |
      v
    Caddy
      |
      v
    Docker proxy network
      |
      v
    Service container

Caddy became the centralized HTTP entry point and Docker's internal DNS was used for container service resolution.

## Key Decision

I introduced the reverse-proxy abstraction **before** adding many more services.

The goal was to prevent future architectural debt rather than wait until direct-port management became unmanageable.

## Troubleshooting / Challenge

The project required validating that services remained reachable through Caddy while direct host web ports were removed.

The resulting operational troubleshooting model separates DNS, Caddy, Docker network membership, and backend application health rather than assuming every friendly-URL failure is a proxy failure.

## Security / Risk Considerations

Centralizing web access reduced unnecessary direct host-port exposure.

It also created Caddy as shared infrastructure, which means proxy configuration and availability require deliberate validation and recovery procedures.

## Enterprise Relevance

This demonstrates:

- reverse-proxy architecture
- Docker networking
- internal DNS/service discovery
- attack-surface reduction
- infrastructure abstraction
- scalable service design
- layered troubleshooting

## Interview Questions

### Why did you choose this approach?

The environment was still small enough to redesign cleanly. Introducing abstraction early avoided multiplying direct host-port dependencies as the platform grew.

### What would you do differently in a production enterprise environment?

I would add managed TLS, stronger identity and access controls, highly available ingress where required, centralized access logging, certificate lifecycle management, monitoring, and formal change control.

### What did you learn from the project?

Abstraction is most valuable when introduced before complexity forces it. Stable user-facing names allow backend infrastructure to change without changing how users reach services.

### What was the biggest technical or operational risk?

Removing direct service exposure without confirming that the proxy path and Docker network could reliably reach every backend.
