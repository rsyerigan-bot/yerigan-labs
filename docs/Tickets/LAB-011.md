# LAB-011 — Centralized Logging

## Objective

Implement centralized log collection, retention, and search for the Yerigan Labs Ubuntu server and Docker environment.

The system should preserve useful operational and security evidence without exposing the logging infrastructure directly to the LAN.

## Business and Operational Value

Centralized logging provides historical evidence that can be searched after an operational or security event.

Without retained logs, investigation is limited to the current state of a system. Events preceding a reboot, service failure, authentication attempt, or container problem may otherwise be difficult or impossible to reconstruct.

LAB-011 establishes the logging foundation required for future detection, investigation, and incident response capabilities.

## Architecture

The logging pipeline consists of:

- Grafana Alloy for log collection and metadata processing
- Grafana Loki for centralized log storage and querying
- Grafana for log exploration and search

Primary data flow:

Ubuntu systemd journal → Alloy → Loki → Grafana

Docker container logs → Alloy → Loki → Grafana

Loki is connected only to required internal Docker networks and is not published directly to the host LAN.

## Log Sources

### Ubuntu Journal

Alloy collects the Ubuntu systemd journal.

This provides host-level evidence including operating system and service activity.

Journal metadata is relabeled to make relevant fields searchable in Loki.

### SSH and Authentication

SSH events are collected through the systemd journal.

SSH activity was successfully queried using:

`{job="systemd-journal", unit="ssh.service"}`

Authentication evidence has high security value because it can help establish when remote server access occurred and provide context around authentication activity.

### Docker Containers

Alloy discovers Docker containers through the Docker socket and collects container logs.

Docker logs provide service and application-level evidence that complements the host-level system journal.

Container logs can be searched globally or filtered by individual container.

## Storage Design

A dedicated LVM logical volume was created for Loki.

Logical volume:

`loki-lv`

Mount point:

`/var/lib/loki`

Allocated size:

`6 GB`

Approximately 3 GB remains unallocated in the volume group for future expansion or other requirements.

The dedicated filesystem separates centralized log storage from the root filesystem and establishes a defined storage boundary.

## Retention

Loki is configured for:

`30 days / 720 hours`

of log retention.

Thirty days was selected as an initial operational baseline rather than assuming unlimited retention.

Actual storage consumption will be observed before determining whether the retention period or allocated capacity should be changed.

## Validation

The following capabilities were validated:

- Loki starts successfully and reports ready
- Alloy successfully forwards journal data to Loki
- Ubuntu journal entries are searchable in Loki
- SSH events are searchable by systemd unit
- Docker logs are collected
- Individual containers can be queried
- Log metadata can be used for structured searches
- Loki storage persists on the dedicated filesystem
- Alloy read-position state persists across container recreation
- Loki and Alloy ports are not published to the host LAN
- Current log ingestion continues successfully after Alloy recreation

## Troubleshooting Finding

During validation, Alloy attempted to replay historical Docker log entries after recreation.

Some historical entries were rejected by Loki because they were older than the acceptable ingestion window. An older entry also preceded the configured Loki schema start date.

Persistent Alloy storage was added using a Docker volume and a defined Alloy storage path so collection state can survive container recreation.

A later recreation produced one stale historical Loki-container entry that was rejected. No additional ingestion errors occurred after the initial startup replay, and current log ingestion continued normally.

This behavior was accepted as a known startup edge condition rather than expanding LAB-011 into unnecessary historical-log recovery work.

## Security Considerations

Loki and Alloy are not directly published to the host network.

The Docker socket is mounted read-only into Alloy for container discovery and collection. Access to the Docker socket remains security-sensitive despite the read-only mount and should be treated as privileged infrastructure access.

Centralized logs may contain security-sensitive operational information and should not be exposed unnecessarily.

## Scope Boundary

LAB-011 establishes collection, retention, metadata enrichment, and search.

The following were intentionally excluded:

- security detection rules
- failed-login detection
- SIEM-style correlation
- automated incident response
- UFW-specific logging
- dedicated Caddy access logging

These capabilities introduce separate security and detection concepts and should build on the validated logging foundation rather than expanding the scope of LAB-011.

## Result

Yerigan Labs now has centralized, retained, and searchable host and container logs.

The environment can preserve evidence about system activity, SSH access, and container behavior for later operational troubleshooting and security investigation.
