# Interview Notes — LAB-010

**Source:** Retrospective Reconstruction

## Purpose

Prepare concise interview talking points from the infrastructure observability and monitoring implementation.

## 30-Second Summary

I built an observability stack using Node Exporter, cAdvisor, Prometheus, Grafana, Caddy, and Home Assistant. Almost immediately, monitoring identified a real problem: the Ubuntu root filesystem was about 99% utilized. I independently validated the alert, investigated the storage architecture instead of deleting data blindly, found unused LVM capacity, expanded the root volume by 10 GB, and reduced utilization to about 66%. I then implemented and tested persistent filesystem alerts with mobile notification delivery.

## Problem / Business Need

Service availability alone did not provide enough information about infrastructure health.

The environment needed historical metrics, health visualization, alerting, and notification before resource problems became outages.

## Technical Approach

The monitoring architecture separated responsibilities:

- Node Exporter — host telemetry
- cAdvisor — container telemetry
- Prometheus — metric collection and storage
- Grafana — visualization and alert evaluation
- Caddy — controlled routing
- Home Assistant — selected mobile notification delivery

The initial production alert focused on root-filesystem utilization.

## Key Decision

When monitoring reported approximately 99% root-filesystem utilization, I validated the condition using operating-system tools before taking corrective action.

Investigation showed the root cause was unallocated LVM capacity rather than reclaimable Docker data.

## Troubleshooting / Challenge

The root logical volume was approximately 19 GB even though substantial capacity remained free in the volume group.

Instead of deleting legitimate Docker data or adding NAS storage, I expanded the root LV by 10 GB and retained additional free VG capacity.

A second challenge occurred when Grafana could not directly reach Home Assistant through the firewall. Rather than widen direct access, alert traffic was routed through Caddy.

Additional testing identified a Docker DNS naming issue and an incorrect webhook identifier, both of which were corrected.

## Security / Risk Considerations

Automated remediation was intentionally separated from monitoring.

A restart might temporarily clear symptoms while destroying diagnostic evidence or concealing the actual cause.

The operational philosophy became:

**Detect → Alert → Preserve Evidence → Investigate → Remediate → Validate**

## Interview Questions

### Why did you choose this approach?

I wanted monitoring to identify developing conditions before they became outages and to provide evidence for troubleshooting rather than simply report whether a service was up.

### What would you do differently in a production enterprise environment?

I would establish longer-term baselines, capacity forecasts, additional alert policies, escalation ownership, redundant monitoring where justified, incident-context capture, and formal response procedures.

### What did you learn from the project?

Availability is not the same as health. Every major service was still running while the root filesystem was nearly full.

I also learned that remediation should follow root-cause analysis rather than assumptions. Docker looked large, but deleting Docker data would not have solved the actual storage-allocation problem.

### What was the biggest technical or operational risk?

Reacting to the 99% utilization by deleting data or restarting systems before understanding why the filesystem was full.
