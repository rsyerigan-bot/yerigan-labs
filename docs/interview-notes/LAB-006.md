# Interview Notes — LAB-006

**Source:** Retrospective Reconstruction

## Purpose

Prepare interview talking points from the infrastructure-as-code migration.

## 30-Second Summary

I migrated Yerigan Labs infrastructure configuration into the Git repository so Git could become the source of truth for desired configuration while runtime state remained outside version control. The project addressed configuration drift and recoverability concerns without making the mistake of committing databases, logs, certificates, private keys, or other runtime-sensitive data.

## Problem / Business Need

Docker and service configuration existed primarily on the live server.

That created configuration-management risk because the desired infrastructure state was not consistently represented in version control.

## Technical Approach

The migration:

- moved infrastructure definitions into the repository
- established Git as the configuration source of truth
- separated configuration from runtime state
- excluded secrets and sensitive runtime data
- used example environment files where appropriate
- preserved live runtime state outside Git
- validated repository and deployed configuration relationships

## Key Decision

The key distinction was:

**configuration belongs in version control; runtime state does not automatically belong in version control.**

## Troubleshooting / Challenge

The challenge was deciding what should be reproducible from Git versus what should remain runtime data.

Files such as databases, logs, generated certificates, private keys, application state, and persistent volumes could not simply be treated like ordinary infrastructure configuration.

## Security / Risk Considerations

Moving infrastructure into Git creates security benefits through traceability but also creates risk if secrets or sensitive runtime material are committed.

The migration therefore explicitly separated configuration, secrets, and runtime state.

## Enterprise Relevance

This demonstrates:

- infrastructure as code
- Git-based configuration management
- configuration/state separation
- secrets awareness
- change traceability
- reproducibility
- documentation of deferred work

## Interview Questions

### Why did you choose this approach?

The environment was growing, and live-server-only configuration would make changes harder to audit, reproduce, review, and recover.

### What would you do differently in a production enterprise environment?

I would add CI validation, peer review, deployment automation, formal secrets management, artifact/version promotion, policy checks, tested rollback procedures, and infrastructure backup/recovery integration.

### What did you learn from the project?

Infrastructure as code does not mean putting everything in Git. Good configuration management requires understanding the boundary between desired configuration, secrets, and runtime state.

### What was the biggest technical or operational risk?

Accidentally treating sensitive or non-reproducible runtime state as ordinary source-controlled configuration.
