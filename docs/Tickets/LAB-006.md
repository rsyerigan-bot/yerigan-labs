# LAB-006 — Infrastructure-as-Code Migration

**Status:** Complete

## Objective

Migrate Docker service definitions and infrastructure configuration from the live Ubuntu server into the Yerigan Labs Git repository so that Git becomes the documented source of truth for infrastructure configuration.

---

## Background

The environment originally contained configuration that existed primarily on the running server.

This created a configuration-management risk because the desired infrastructure state was not consistently represented in version control.

LAB-006 established a clearer separation between version-controlled configuration and runtime application state.

---

## Success Criteria

- [x] Docker service definitions represented in the Yerigan Labs repository
- [x] Caddy configuration represented in the repository
- [x] Homepage configuration represented in the repository
- [x] Runtime state excluded from version control
- [x] Secrets excluded from version control
- [x] Example environment files used where appropriate
- [x] Git established as the source of truth for infrastructure configuration

---

## Architecture

### Before

    Live Ubuntu Server
            |
            +-- Configuration
            +-- Runtime State
            +-- Service Data

    Primary source of truth:
    Running server

### After

    Yerigan Labs Git Repository
            |
            +-- Version-controlled configuration
            |
            v
    Live Ubuntu Server
            |
            +-- Runtime state
            +-- Service data
            +-- Secrets

Git describes the intended infrastructure configuration.

Runtime state remains outside version control and requires an independent backup strategy.

## Known Issues and Deferred Work

- Deployment directly from the repository is not yet automated.
- Runtime state requires a separate backup and restore strategy.
- Infrastructure-as-Code coverage can be expanded as additional services are deployed.

These items were intentionally deferred rather than treated as failures of LAB-006.

---

## Lessons Learned

- Configuration and runtime state serve different purposes and should be managed differently.
- Git should describe the desired environment rather than capture the complete runtime condition.
- Databases, logs, certificates, secrets, and application state should not be committed merely because they exist beside configuration files.
- Infrastructure becomes easier to reproduce and audit when configuration has an intentional source of truth.
