# LAB-012 — Vulnerability Validation and Controlled Exploitation

**Status:** Complete — controlled vulnerability validation and impact verification completed

## Objective

Demonstrate a disciplined vulnerability-assessment workflow by progressing from previously collected service-enumeration evidence through vulnerability research, validation, controlled exploitation, impact verification, and post-test cleanup within an isolated cyber range.

---

## Background

RED-003 identified multiple services on the authorized Metasploitable 2 target, including FTP running vsftpd 2.3.4.

A product/version string can identify a candidate for vulnerability research, but it does not by itself prove that a vulnerability exists or is exploitable.

LAB-012 / RED-004 continues the assessment by evaluating one identified service and determining whether the suspected vulnerability can produce demonstrable security impact.

## Architecture

The existing isolated cyber range was retained.

KALI01 (`192.168.50.10`) communicated with TARGET01 (`192.168.50.20`) across the isolated `vmbr1` network.

TARGET01 exposed vsftpd 2.3.4 on TCP/21. TCP/6200 was confirmed closed during the pre-exploitation baseline and became accessible following successful triggering of the vulnerable behavior.

The vulnerable target remained isolated from the home LAN and Internet-facing systems.

## Known Issues

- Metasploit initially selected a payload requiring additional callback configuration that was unnecessary for demonstrating the underlying vulnerability.
- An attempted bind-shell payload did not create a Metasploit session even though the module reported that the backdoor had spawned.
- Direct protocol interaction and independent port validation were used to isolate and verify the underlying vulnerability behavior.
- TARGET01's manually assigned lab IP configuration was temporary and required restoration after a VM reboot.

---

## Lessons Learned

- A service/version fingerprint identifies a vulnerability-research candidate; it does not prove vulnerability.
- Framework output should be independently validated when practical.
- Exploit mechanism and payload behavior are separate concepts.
- Successful vulnerability triggering does not automatically mean a usable session has been established.
- Baseline and post-action measurements provide stronger evidence than isolated tool output.
- Root access does not expand assessment authorization.
- Testing should stop when sufficient evidence has demonstrated the agreed security impact.
- Troubleshooting failed exploitation attempts can provide more understanding than immediately obtaining a successful shell.
