# LAB-007 — Home Platform Foundation

**Status:** Complete

## Objective

Establish organizational, naming, usability, and recovery-design standards for the Yerigan Home Assistant platform before broad device onboarding and automation development.

---

## Background

Home automation environments can become difficult to operate when devices are added before naming conventions, areas, dashboards, and platform standards are defined.

LAB-007 focused on establishing those standards before expanding the Home Assistant environment.

The goal was to build a platform that remains understandable, maintainable, family-friendly, and adaptable as devices and automations are added.

## Platform Organization

Home Assistant should represent the physical home using understandable locations and functional names.

Areas should reflect real household spaces such as:

- Garage
- Office
- Kitchen
- Living Room
- Bedrooms
- Bathrooms
- Entry areas
- Outdoor areas
- Network and infrastructure spaces

Exact areas may change when the platform is deployed in a different home.

---

## Device Naming Standard

Device names should describe function and location rather than manufacturer whenever practical.

Preferred examples:

- Kitchen Ceiling Light
- Living Room Lamp
- Front Door Lock
- Garage Motion Sensor
- Primary Bedroom Curtains
- Front Porch Camera

Avoid manufacturer-centric names such as:

- Kasa Plug
- Aqara Motion
- SwitchBot Curtain

Manufacturers and hardware may change while the function of the device usually remains consistent.

---

## Entity Naming Philosophy

Entity identifiers should remain predictable and understandable.

Examples include:

- `light.kitchen_ceiling`
- `lock.front_door`
- `camera.driveway`
- `binary_sensor.garage_motion`

Consistent entity names improve automation readability, troubleshooting, and long-term maintenance.

---

## Dashboard Philosophy

The platform should avoid placing every function on one large dashboard.

Separate dashboards should serve different audiences and purposes.

### Family Dashboard

Designed for normal household use.

Examples:

- Weather
- Doors
- Locks
- Garage
- Lights
- Thermostat
- Security status
- Good Night controls

Technical infrastructure details should generally remain hidden from this view.

### Operations Dashboard

Designed for infrastructure administration.

Examples:

- Network status
- Proxmox
- Docker
- Pi-hole
- Server health
- Internet status
- Power information

### Security Dashboard

Designed for household security information.

Examples:

- Cameras
- Doorbell
- Door locks
- Motion sensors
- Smoke detection
- Water-leak sensors

### Automation Debug Dashboard

Designed for engineering and troubleshooting.

Examples:

- Entity states
- Sensors
- Helper entities
- Automation traces
- Diagnostic information

## Backup and Recovery Philosophy

Home Assistant configuration and automation state must eventually be recoverable without rebuilding the platform from scratch.

The intended backup model includes:

- Local backup capability
- Future NAS-based backup storage
- Optional off-site or cloud copy where appropriate
- Documented restore procedures
- Periodic restore validation

At the completion of LAB-007, these requirements were documented but a complete backup and restore system had not yet been implemented.

Backup implementation and restore testing remain future engineering work.

---

## Architecture Principles

Home Assistant acts as the primary household automation platform.

Vendor ecosystems should integrate into the platform rather than independently defining the overall automation architecture.

Where practical:

- Automations should reference functional entities rather than specific hardware.
- Household functions should retain manual fallback controls.
- Critical automations should prefer local operation.
- Device onboarding should occur incrementally.
- Family usability and reliability take priority over unnecessary complexity.

## Known Issues and Deferred Work

- Production backup automation has not yet been implemented.
- Backup restore procedures have not yet been tested.
- NAS-based backup storage remains future work.
- Final floors and areas may change following permanent home deployment.
- Advanced presence and occupancy capabilities remain future work.
- Broad smart-device onboarding remains intentionally incremental.

---

## Lessons Learned

- Organizational standards should be established before large-scale device onboarding.
- Functional names age better than manufacturer-based names.
- Different users need different operational views.
- Automation logic should depend on stable abstractions rather than individual pieces of hardware where possible.
- Backup design is not the same as backup implementation.
- A recovery strategy is incomplete until restoration has been tested.
