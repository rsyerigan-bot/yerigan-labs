## 30-Second Summary

I hardened remote administration of my Ubuntu homelab server by replacing password-based SSH access with Ed25519 public-key authentication and disabling remote password and root login. During implementation, I discovered that an earlier OpenSSH configuration file was overriding the setting I expected, so I validated the effective SSH configuration rather than relying only on the file I had edited.

## Problem / Business Need

Remote server administration needed a stronger and more repeatable authentication model than password-based SSH.

The goal was to improve security while preserving reliable administrative access.

## Technical Approach

- Generated an Ed25519 SSH key pair.
- Configured public-key authentication.
- Disabled SSH password authentication.
- Disabled root SSH login.
- Preserved local authentication for sudo and console recovery.
- Validated SSH syntax and effective configuration.
- Tested that key authentication succeeded and password-only authentication failed.

## Key Decision

The important decision was to validate the **effective OpenSSH configuration**, not merely assume that the configuration file I edited controlled the final behavior.

## Troubleshooting / Challenge

Password authentication remained available even after the hardening configuration appeared correct.

Investigation showed that OpenSSH configuration precedence mattered. An earlier configuration file contained `PasswordAuthentication yes`, so the intended setting was not taking effect.

The fix was to place the hardening configuration at the appropriate precedence and then verify the effective settings.

## Security / Risk Considerations

The change reduced exposure to password-based SSH attacks while preserving a recovery path through local or Proxmox console access.

A working administrative session should be preserved during SSH configuration changes to reduce lockout risk.

## Enterprise Relevance

This demonstrates:

- change-risk management
- recovery planning

## Interview Questions

### Why did you choose this approach?

Public-key authentication provides stronger remote authentication than relying on reusable passwords and is appropriate for administrative SSH access.

### What would you do differently in a production enterprise environment?

I would integrate the configuration into formal configuration management, centralized identity where appropriate, approved key lifecycle procedures, logging and monitoring, change control, and documented break-glass access.

### What did you learn from the project?

A configuration file can look correct while the effective system configuration is still wrong. Validation needs to test the control that is actually active.

### What was the biggest technical or operational risk?

Locking myself out of the server while changing SSH authentication.
